# 司衡引擎 sih-engine

如果你让 AI 写过代码，这些场景大概不陌生：

- **它比你快太多了。** 一个晚上几百个文件改完，早上你面对的是一个大部分没看过的项目。进度到哪了、还差什么、哪些已经可靠，说不清。项目越大，这个感觉越重。
- **你想要 A，它交付 B。** 需求在对话里明明说清楚了，落到代码就变形。等你看出来，错误的地基上已经盖了三层楼。
- **改一处，漏一片。** 让它重写一个功能，主要文件改了，引用点漏了一半；顺手做的「小优化」让别的模块悄悄崩了，然后你花几倍的时间回来修。
- **坏写入查无对证。** 为了让测试变绿，它删校验、注释断言。事后你能 revert 代码，却查不到它当时为什么这么改，那一步的意图永远丢了。

前四个是急痛。还有三个慢一点的：AI 每次开新会话都失忆，没人记得项目全貌；多个 Agent 并行开发时各干各的，没有共同事实；项目在一次次「看起来能跑」里慢慢烂成没人敢动的黑箱。

这些麻烦背后是同一件事：AI 出活的速度，超过了人理解和审查的速度。

司衡引擎管的就是这条速度差。它不让 AI 变慢，也不替你思考，而是把治理装在两头：

**生成之前**，把你的意图拆解清楚、把项目上下文注入给 AI，让它沿着你的意图生成，而不是沿着它猜的意图。

**生成之后**，写入、验收、留痕交给确定性程序：越权的拦下，该记的留痕，异常推给人，你不巡检日志。

## 七个痛，六个组件加一套租约

| 你的痛 | 司衡的件 | 它干什么 |
|---|---|---|
| 要 A 得 B | **三问** | 开工前把「我要什么」拆解成可检验的问题，拆到答得上「怎么算做成」，作为意图合同上链。链上的意图事后不可改，验收、审计、追责都以它为基准，堵死「事后合理化」 |
| 不知道项目走到哪了 | **视图与巡检** | 治理目标被机械回算成三态报告：达成（完成）、在飞（进行中）、沉底（搁浅被遗忘的）。你读报告和告警，不读改动日志。判据本身注册在册，改动要走治理流程，不随口定 |
| AI 每次会话都失忆 | **温故** | 项目的治理档案（决策、变更、原因）按主题、用词、事件、时间四条轴可检索。新会话的 AI 靠召回拿项目全貌，不靠猜 |
| 范围外的写入、多 Agent 互相踩脚 | **租约与锁** | 修改开工前立租约：声明这次动哪些文件，锁住它们，别的会话写同一文件会被拒或排队；收约时逐文件对表，没声明过的改动会被点名 |
| 看不懂 AI 的技术方案 | **得一** | 同一个判断让模型独立作答（默认五遍），收敛才放行，判定由确定性程序按已签规则执行，不收敛的升级给人。你不需要看懂方案细节，也能得到一个不依赖单次抽签的裁定。要说边界：它压的是方差不是偏差，模型系统性地想错时五遍照样错，所以重大裁决保留人的一票否决，不收敛的升级给人 |
| Agent 协作没有共同事实 | **哈希链（书简）** | 所有治理动作进同一条链：谁在何时改了什么、为什么，一条命令复算全链。协作的信任从「互相盯」变成「共同对账」 |
| 改一处漏一片、不懂编程质量全靠赌 | **参验与模板** | 规格先行迫使动手前把影响面写清楚，收约时的完备度门机械检查「先立规格、有测试」。它不教编程，质量关卡只要求流程走完，不懂编程的用户按模板走，产出的项目流程、规格、测试、留痕齐全，接手者（人或 AI）有据可依；代码本身的好坏，它不保证 |

关于最后一行多说一句：让不具备编程能力的用户做出可维护的项目，是这个系统明确的设计目标之一。SDD／TDD 模板引导的是流程，机械闸保证流程不被跳过。

一句丑话说在前头：这套闸约束的是走治理通道的 agent，即通过 MCP 工具写入的模型客户端。它不是对抗恶意程序的沙箱，绕开工具直接改文件、删掉治理树的进程，拦不住；通道内的坏改动（比如声明范围内偷偷删校验）也不会被当场识破。但拦不住不等于看不见：未过闸的主树写入会在下次巡检对表时被点名为无主改动，历史篡改会在验链时整条暴露，通道内每一步都留着不可改的痕。要防物理毁灭，请用文件系统权限和备份，那是另一层的事。

这套设计来自一次真实的失败。我们之前造过一版没有闸门的同类系统：AI 的生成速度和人的审查速度之间的差距把团队淹没了，日志没人看，变更没人审，最后整个仓库报废重来。这一版的第一设计假设就是那次的验尸报告：人的注意力是稀缺资源，系统必须自己消化绝大多数操作，人只处理异常。

## 不信可以自己验

这个项目的每条主张都设计成可以用命令复核。编译之后跑这两条：

```bash
# 验链：最近一日治理链整链复算，status valid 即完整未篡改
latest=$(find sih/event/trail -name '*.ndjson' | sort | tail -1)
target/debug/scribe verify --trail "$latest"

# 巡检：当前治理状态六判据（达成／在飞／沉底）与未决事项路由
target/debug/critsweep --at $(date +%F) --root ..
```

critsweep 的 --root 指工作区根；单仓克隆时在飞面会降级并如实显示，不会假装正常。

## 五分钟跑起来

```bash
cargo build
```

工具编译后都在 `target/debug/` 下，上面两条验证命令此刻就能跑。想看系统治理一个真实项目时的完整样子，读 doc/guide/user-guide-v1.md，半小时走读一个真实批次。

## 接入你自己的项目

司衡治理你的研发流程，不接管你的代码。接入就一步：把 stdio 配置块加进你的 MCP 客户端，连上。

**首次连接会自动开域**：引擎发现 SIH_ROOT 指向一个还没治理过的 git 项目时，自动签发标识牌（令牌的作用是绑定治理空间，不是密码）、建 sih 治理树、落开域首笔并自验，全程不需要浏览器或管理台；`sih/` 目录会自动写进 `.git/info/exclude`，治理数据不进你的 git，项目照常公开。自动动作会在 stderr 里如实告知，不静默。

手动形态也有（想先看会发生什么再开域的人用）：

```bash
cd <引擎工作区>/sih-engine
target/debug/sihmcp bootstrap <项目根> --by <事由> --token-id <短串>
```

或者起本地管理台走两步确认：`SIH_TRANSPORT=http target/debug/sihmcp`，浏览器开 http://127.0.0.1:8765/tokens。

之后按 doc/guide/agents-template-v1.md 的模板裁剪会话启动项。日常运行无后台服务、无监听端口。单页走读见 doc/guide/adoption-guide-v1.md（注意其第二节「先签发后 init」的旧序列已被现行签发闸取代，以本页流程为准，指南修订候裁）。

## MCP 接入

引擎内置 Rust 实现的 MCP 服务端，编译产物是 `target/debug/sihmcp`。缺省 stdio 形态，一个进程一条连接治理一个项目。在客户端配置里加一块（路径换成你机器上的绝对路径）：

```json
{
  "mcp": {
    "servers": {
      "sih": {
        "type": "stdio",
        "command": "<引擎仓绝对路径>/target/debug/sihmcp",
        "env": {
          "SIH_ROOT": "<你要治理的项目根>",
          "SIH_MCPLINE_CODE_ROOT": "<引擎工作区根>"
        },
        "enabled": true,
        "timeoutMs": 60000
      }
    }
  }
}
```

- SIH_ROOT 显式指项目根最稳；不写就从当前目录向上找标记
- SIH_MCPLINE_CODE_ROOT 指引擎工作区，写面的书简与租约二进制从这里解析；引擎与治理根同源布局时可省
- 多个项目就是多块配置，一客一域
- 注意：`bootstrap --client-config` 自动生成的是 HTTP 形配置，走 8765 端口；用 stdio 就照上面手写，两种形态不可混用

需要多域接入和令牌管理台时，再启用 8765 的 HTTP 面，见 doc/design/DES-015。

## 工具面

读面九具，只读：查链 `chain_query`、验链 `chain_verify`、状态巡检 `critsweep`、心跳 `heartbeat`、锁面读数 `locks_read`、档案检索 `retriever_recall`、立名指引 `naming_guide`、查词 `nomenclator_query`、文档核查 `nomenclator_check`。

写面十具，全部要求先 `lease_open` 立会话，未立会话一律拒写：`lease_open`、`record_intent`、`record_append`、`record_park`、`lease_lock`、`lease_unlock`、`lease_wait_turn`、`lease_claim`、`lease_commit`、`lease_close`。本地可信环境另有两具直写位 `record_direct` 与 `lease_unclaim`。三个 record 开头的具是三类留痕：意图、事件、停泊。逐具契约见 doc/spec/SPEC-023。

## 什么时候不该用它

- 低风险、快速迭代、写坏了大不了重来的项目。治理的手续成本会超过它的收益。
- 没有审计需求、不关心「谁在什么时候改了什么、为什么」的场景。
- 你想让 AI 自主探索一个原型。司衡约束的是严肃工程面的写入，不加速探索。

司衡为错误代价高、可审计性本身就是需求的场景设计。如果你的项目不在上面的名单里，现在的你不需要它。

## 设计信念（可选深度）

上面的一切建立在五条工程基线上（正典全文在 doc/governance/BASELINE-v1.md，哲学推导在 sih-philosophy 仓，不读不影响用）：

1. 治理操作只由确定性程序执行。LLM 只生成符号材料，没有写入权。
2. 假设人类注意力是稀缺资源。LLM 的生成速度和人的审查速度之间是结构性不对称，这是上一版仓库用报废换来的教训。
3. 人只在收到告警时介入，不看原始日志。
4. 所有写入可追溯、可机械校验、历史不可篡改。LLM 的不可复现输出不作为治理决策的最终依据。
5. 治理能力的延伸方向是减少 LLM 参与，不是增加。但不生成不等于不引导：引擎用前置约束、意图锚定、上下文加载锁定 LLM 生成的方向。

## 往深处走之前：你会遇到的词

读 doc/guide 和源码时会撞见一批内部词，主文刻意避开了它们，这里先备好：

| 词 | 人话 |
|---|---|
| 租约 lease | 一次治理批的生命周期：立约开工、租内加锁、提交、收约 |
| 书简 scribe | 链上留痕的唯一写入通道 |
| 泊界 parking | 未决事项的有界停靠区，入泊出泊都上链 |
| 判据扫 critsweep | 定期回算治理目标现态的机械巡检 |
| 得一 attractor | 收敛裁决：限定条件内得出唯一方向；得不出一就归人诊断 |
| 执契 tally | 确定性核对与终签脚本，人和 AI 都不能代签 |
| 检词 nomenclator | 术语登记册与文档用词核查 |
| 核阅 scrutinator | 文档规则核验；本体不带规则，规则全在数据包里 |
| 围堰 | 先在引擎仓外孵化工具、验证后再融回的隔离区 |
| 红证 | 失败的测量与对己不利的读数也入档，事后不删不改 |
