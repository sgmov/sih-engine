# 仓库结构

司衡引擎（sih-engine）需要确定项目文件的存放路径，本决策定义仓库的结构性元规则：顶层节点分界、文档类型清单、节点关系视图。
文档身份由其存放路径与文件名共同确定，类型归位判据的细化实施由各类型特异规范设计文档承载，本决策不重复定义。

按司衡哲学结构收敛对照的双视角论证：结构性元规则归决策文档，类型特异规范归设计文档。

- 本决策：仓库结构性元规则
- 通用格式规范跨类型一致，由后续设计文档承载
- 各类型特异规范由对应设计文档承载，覆盖必选章节、必选元素、归位判据展开
- 审阅机制类型归属由审阅痕迹决定，由后续提案承载

## 概览 {#overview}

- 文档区与治理区按消费模式分界，源码、测试、工具按工程职责分界::[顶层节点分界](#root-node-boundary)
- 节点树表达逻辑节点关系，不决策物理存储方式::[全节点树](#full-node-tree)
- 围堰期物理节点收编入树，逻辑与物理的对应经映射表声明，融回迁移不改写痕迹::[围堰物理对应与归位映射](#cofferdam-mapping)
- 文档区按文档类型组织，体系定义作为设计子节点存在::[文档区结构](#doc-area-structure)
- 治理区按事件与状态本体二分::[治理区结构](#sih-structure)
- 挑战与报告归治理区，涵盖消费模式判据::[挑战和报告归治理区](#challenges-reports)

### 顶层节点分界 {#root-node-boundary}

仓库设 5 个顶层节点，分界依据分为两类：消费模式与工程职责。

1. 消费模式
   1. 文档区
   2. 治理区
2. 工程职责
   1. 源码
   2. 测试
   3. 工具集

#### 消费模式 {#uname1}

文档区与治理区的分界依据是内容的消费模式，而非内容类别。

文档区
: 存放被持续引用的活跃文档
: 人类创作、人类直接查阅的项目资产，创建后长期活跃，被代码、新文档、新决策持续引用

治理区
: 存放引擎运行时消费的数据、引擎产出的过程文档、治理痕迹
: 产出后在治理流程中被消费，之后不活跃
: 主要消费者是引擎运行时，人类仅在审计时查阅

#### 工程职责 {#uname2}

- 源码、测试、工具的分界基于工程职责
  - 源码存引擎核心源代码，是 MCP server 与内部模块的承载，编译产出引擎可执行文件
  - 测试存测试代码，是验证源码的工程产物。工具存独立 CLI 工具，每个工具是独立 Cargo 项目，有独立 Cargo.toml，独立编译为可执行文件，可单独分发
  - 工具与源码的分界判据是是否独立编译分发，需要独立二进制约 CLI 工具归工具，引擎内部模块归源码
  - 三者的内部组织分别由架构决策、测试方法论决策、工具各自的实施设计承载，不在本决策范围

挑战和报告被归入治理区不是因为它们本质上和决策不同，决策也是治理过程的产物。区分在于消费模式：决策创建后被持续引用，代码引用它、新决策引用它。挑战和报告产出后被消费一次，触发新决策或关闭挑战，之后归档不再活跃。此判据为设计推论（design-corollary），非哲学必然：若实践中挑战或报告被频繁持续查阅，消费模式接近决策，应移回文档区。

### 全节点树 {#full-node-tree}

仓库顶层节点关系如下。节点树表达的是逻辑节点的层级与归属关系，不是物理存储结构。树中的每个节点不预设物理实现：可能是文件系统的一个目录或文件，也可能是数据库的一张表或一个视图，也可能是缓存层的一个键值空间。节点的物理存储方式是工程实现细节，由后续设计文档承载，本决策不决策。物理形态包括文件、数据库、持久化、缓存、内存等。

文档区与治理区展开到子节点，源码、测试、工具不展开。

````filetree

├── AGENTS.md                      代理引导层，引擎域指令
├── doc/                           被持续引用的活跃文档，人类直接查阅
│   ├── requirement/               需求/意图   REQ-NNN-slug，物理待建
│   ├── decision/                  决策文档    DEC-NNN-slug
│   ├── design/                    技术设计    DES-NNN-slug
│   │   └── architecture/          体系定义    ARC-NNN-slug
│   ├── spec/                      规格定义    SPEC-NNN-slug
│   ├── governance/                规约        GOV-NNN-slug
│   ├── knowledge/                 知识库      KNOW-NNN-slug
│   ├── research/                  研究记录    日期命名，非编号族
│   ├── proposal/                  提案        PRO-NNN-slug
│   └── CASCADE.json               级联关系投影，逻辑归 sih/state/graph
│
├── sih/                           司衡引擎治理层，治理过程与痕迹
│   ├── event/                     事件层（发生过的事件，只追加写）
│   │   ├── trail/                 治理动作留痕，物理围堰于 sih-tools/scribe/trail
│   │   ├── feedback/              反哺信号
│   │   ├── challenge/             挑战记录
│   │   └── report/                审查报告
│   ├── state/                     状态层（当前投影）
│   │   ├── registry/              文档身份与状态登记，物理待建
│   │   ├── graph/                 文档关系投影，物理暂挂 doc/CASCADE.json
│   │   ├── view/                  派生视图，物理待建
│   │   ├── plan/                  待执行意图编排投影
│   │   └── calibration/           参验机制标定基准集
│   └── static/                    静态档，审计链存档
│
├── task-packages/                 治理任务包，T6 载体
├── skills/                        引擎技能权威源，投影至工作区 .agents/skills
├── parking/                       主线泊界材料件，名册在 doc/governance/PARKING-v1.md
├── OPEN-QUESTIONS.md              开放问题工作记忆，消化后迁移
├── state/                         早期任务投影位，逻辑归 sih/state/plan，归位待迁移
├── src/                           源代码
├── tests/                         测试代码，Cargo 约定即 tests
├── examples/                      Cargo 示例位，属源码域约定
├── fixtures/                      测试夹具位
├── probes/                        探针脚本位，测试支撑
└── tools/                         独立 CLI 工具，物理围堰于外仓 sih-tools
````

tmp 与 target 为临时与构建区，不入节点树，清理纪律由后续批承载。

### 围堰物理对应与归位映射 {#cofferdam-mapping}

围堰期治理能力外切于 sih-tools，逻辑节点与物理载体经下列五件对应。本节是融回迁移的基准，即迁移动作按对应执行，不由实施批重推。

sih/event/trail
: 物理载体 sih-tools/scribe/trail 即书简围堰，归位动作融回迁移且历史行不改写

状态层登记族
: 物理载体 sih-tools/lease/ledger 即租约台账围堰，归位动作融回接引擎状态层登记

tools 独立 CLI 工具
: 物理载体外仓 sih-tools 即各工具契约持 CONTRACT.md，归位动作融回按贡献度逐件评估即位 sih-engine/tools 或独立发布

sih/state/graph
: 物理载体 doc/CASCADE.json，归位动作迁移至 sih/state/graph

sih/state/plan
: 物理载体顶层 state/tasks 早期位加 sih/state/plan 现位，归位动作归并至 sih/state/plan

归位三原则。第一事件只追加即 trail 历史行不改写，迁移复制不搬改。第二旧路径不失效即历史记录与外部引用里的旧路径经本节解析到归位后节点，痕迹对账以本节为基准。第三迁移动作本身走批留痕即每次归位是一个治理批次，非静默搬移。

### 文档区结构 {#doc-area-structure}

文档区以文档类型为组织维度，每种类型一个子节点。文档类型是归位的确定依据，一份文档属于什么类型是确定的，类型并不代表它属于哪条治理条线、哪个范式。

司衡引擎（sih-engine）定义文档区七大类型，按以下文档类型组织，所有类型均进入治理链条。本决策定义结构性元规则，覆盖类型清单与子节点关系。各类型的详细内容规范由对应类型特异规范设计文档承载，覆盖必选章节、必选元素、归位判据、自动校验规则。

- 类型清单：
  - 需求文档类型（requirement）
  - 决策文档类型（decision）
  - 设计文档类型（design），含体系定义子类型 architecture
  - 规格文档类型（spec）
  - 规约文档类型（governance）
  - 知识库文档类型（knowledge）
  - 提案文档类型（proposal）

#### 体系定义子类型 {#architecture-subtype}

体系定义（architecture）描述系统的本体结构：治理条线总纲、横切维度、范式清单、哲学骨架压缩。这些是系统架构层面的声明，几乎不迭代，引用链条固定。

体系定义作为设计文档下的子节点存在，不独立为顶层类型。理由：

- 体系定义与技术设计经常交叉引用。设计文档常引用体系定义，体系定义也常引用设计文档。
- 体系定义体量小、迭代频率低，独立为顶层类型会增加顶层节点膨胀
- 同一类型下子节点区分是逻辑隔离的最小代价方案

命名规则：NNN-slug，与设计文档共享前缀族，共同组成 DES-ARC，标识为体系定义子类型子集。命名规则的物理形态由后续设计文档承载，可能形态包括单文件、文件夹集群、数据库记录等。

### 治理区结构 {#sih-structure}

治理区接受司衡哲学指导，按事件与状态本体二分组织治理数据。事件与状态二分是归位的确定依据：一份治理数据是发生过的事件还是当前的投影是确定的。哲学依据详见 § 关系图谱。

司衡引擎定义治理区两层，按以下层级组织：

- 层级清单：
  - 事件层（event）
  - 状态层（state）

#### 事件层 {#event-layer}

发生过的事件，只追加写，产出后归档不再活跃。包含子节点：

- 治理动作留痕（trail）：治理主体动作的实时伴随留痕
- 反哺信号（feedback）：工程层对哲学层的张力登记
- 挑战记录（challenge）：外部对治理对象的质疑
- 审查报告（report）：检验的事件产出

#### 状态层 {#state-layer}

治理对象的当前投影，可查询、可变化。包含子节点：

- 文档身份与状态登记（registry）：文档治理元数据的登记簿。权威源是文档区，登记是状态的投影。
- 文档关系投影（graph）：文档间派生、取代、关联的关系结构
- 派生视图（view）：从登记与事件层合成的当前状态视图
- 待执行意图编排投影（plan）：待执行治理意图的当前编排状态。plan 承载任务编排的当前投影，含阶段划分、输入输出、串行约束、参验点。plan 是状态层节点，区别于事件层的 task_completion 事件即已完成动作的留痕。
- 参验机制标定基准集（calibration）：参验机制的标定基准数据。calibration 承载用数学方法标定参验精度的基准值与原始数据，含采样收敛率、tie 率、auto-decide 率、收敛曲线、版本漂移效应。calibration 的实验设计受微积分与概率论与数理统计启发，用 N 次隔离采样标定语义判断的收敛基准。calibration 是已标定的基准值，不是探索性实验。

事件层与状态层的物理载体由后续设计文档承载，本决策只定本体二分的逻辑结构。物理载体包括但不限于：文件系统目录与文件、关系数据库的表与视图、键值缓存、内存结构。事件与状态的本体二分对物理载体免疫：无论物理实现如何，发生过的事件与当前的投影在本体上仍然不同。

### 挑战和报告归治理区 {#challenges-reports}

挑战（challenge）是对既有决策或现状的质疑。报告（report）是检验与审查的产物。

挑战的最终产物是决策，报告的最终产物要么是反哺信号、要么是新需求。它们产出后被消费一次，之后归档不再活跃，消费模式归事件层。

## 决策后果 {#decision-consequence}

### 决策正面后果 {#consequence-positive}

- 文档归位有确定答案：按消费模式二分与按类型组织，任何文档都能确定归属节点
- 治理区按事件与状态本体二分，分类轴承接哲学命题，即留痕是构成性条件，非工程臆造
- 治理区节点名贴合实体本体，避免静态/动态二分的名字与实体错位。贴合性经立名失败检测，覆盖治理动作留痕、登记、视图等节点。
- 内容与痕迹节点分离，正文清爽，治理信息集中在治理区
- 降级可用：引擎故障时，人类仅凭文档区节点结构与状态层就能了解项目核心信息
- 元规则与实施规则清晰分工：决策文档定方向，设计文档定细则，规约文档定流程

### 决策负面后果 {#consequence-negative}

- 治理事件链在文档区与治理区之间节点不连续，须靠关系图逻辑串联
- 文档区按类型分会打断治理条线的节点连续性，依赖关系图维护
- 类型归位判据需查各类型特异规范设计文档，本决策不承载完整判据
- 事件层承载治理主体动作的多类留痕，存在过载可能，其节点内部组织与物理载体由后续设计文档承载

## 备选方案 {#alternative-plan}

按治理条线组织文档区目录
: 已拒绝
: 一条治理条线的产物散布在多种文档类型里，按条线分目录会导致同一份文档无法归位，且违背降级可用原则。当前决策：按文档类型组织。

本决策同时承载元规则与类型归位判据
: 已拒绝
: 混淆结构性元规则与类型特异规范的分工。按结构收敛对照的双视角论证，元方向归决策，实施规则归设计。

独立的「文档类型格式」决策群
: 已撤销
: 类型特异规范由各类型特异规范设计文档承载，不独立为决策群。

## 关系图谱 {#relation-graph}

- 本决策定义仓库的结构性元规则：顶层节点分界、类型清单、节点关系视图、治理区事件与状态二分
- 本决策被约束于：文档格式决策的「文档不自包含」原则，以及「文档身份由存放路径与文件名共同确定」的身份规则

- 治理区子节点命名承接：立名本体论 [^5] 的立名失败检测
- 本决策的元规则下沉至各类型特异规范设计文档与通用格式规范设计文档
- 物理存储方式，包括文件、数据库、持久化与缓存，以及事件层物理组织与治理动作留痕过载解法，均由后续设计文档承载，不在本决策范围
- 后续各类型的必选章节、归位判据、自动校验规则详见对应类型特异规范设计文档
- 审阅机制由后续提案承载，类型归属由审阅痕迹决定
- 源码内部组织由架构决策负责，测试内部组织由测试方法论决策负责，工具内部组织由各工具各自的实施设计承载，均不在本决策范围
- 承接：结构收敛对照[^6]的元层处理差异，即元治理环节与元层独立的区分

## 认识论立场 {#epistemic-stance}

本决策的认识论标签混合两种。

核心决策为设计推论（design-corollary），是工程设计选择，非逻辑必然。覆盖项：文档区与治理区分界判据、按类型组织、挑战和报告归治理区、治理区子节点命名、体系定义作为设计子节点、物理存储方式归设计文档。

治理区事件与状态二分为外部锚定（external-anchor），承接哲学命题。五个留痕命题全部指向事件层；状态层是文档不自包含元原则的工程化投影，即治理信息归独立索引，状态层即该独立索引的承载节点。

可证伪条件一
: 若实践中发现「按类型组织导致某条治理条线的文档难以追踪，且治理区关系图未能有效弥补」，则需重新考虑是否引入治理条线维度的逻辑组织

可证伪条件二
: 若降级场景，即引擎故障状态下，人类无法仅凭文档区节点结构与状态层了解项目核心信息，则降级可用原则失效

可证伪条件三
: 若挑战和报告归治理区后，外部审阅者因无法在文档区找到治理过程而反复挑战，则消费模式判据需重新审视

可证伪条件四
: 若体系定义独立为顶层类型的需求出现，体现在体量增长或迭代频率提升等方面，则需重新评估当前子节点方案

可证伪条件五
: 若实践中出现既不是事件也不是状态的第三类治理数据，则事件与状态二分失效，需扩展为三分或重选分类轴

可证伪条件六
: 若实践中发现治理动作留痕过载致命，且数据库方案无法缓解，则事件层需节点分割。过载判据是多类治理动作留痕混在一起导致检索困难。

## 附录 {#appendix}

### 文档区与治理区的关联机制 {#doc-sih-linkage}

文档区正文与治理区痕迹通过文件名编号关联。同一编号在治理区三个节点产生痕迹：

- 文档身份与状态登记承载该编号的身份与状态登记
- 文档关系投影承载该编号与其他编号的派生、取代、关联关系投影
- 治理动作留痕承载该编号建立与演化的治理动作留痕

派生链，例如需求、规格、设计这样的链，通过文档关系投影串联：上游编号与下游编号的派生关系在文档关系投影节点登记，文档区各正文之间不直接维护派生链接。

文件名不可变约束：一旦文档创建，其编号与路径别名固定，不得重命名。重命名会断开文档区与治理区的关联链。路径别名需要变更时，通过取代机制创建新文档，例如新决策取代旧决策，而非改名旧文档。

### 物理存储最小约束 {#physical-storage-minimum}

按审计报告（audit-047）诊断「委托链过长导致下游可以做出任何选择」修订，下游设计文档至少须满足：
