# 代码与文档统一参验机制

本提案登记一个待验证的设计方向：等 sih-engine 有实际代码后，设计代码与文档统一的参验机制。本提案不立即实施，登记以防遗忘。

## 概览 {#overview}

- 代码参验路径二未设计未验证，文档参验已由 Phase 2 验证::[核心问题](#core-problem)
- 三个候选含独立设计、直接复用、SDD 加 TDD 嵌合缝隙检查::[候选方案](#candidates)
- 推荐 SDD 加 TDD 嵌合下查三个缝隙，含回退方案::[推荐方案](#recommended)
- 哲学基础 PRO-07 鉴反映与 PRO-08 应辨处置适用于代码::[哲学检索](#philosophy-search)
- 四个待定问题含范式确认与实验验证::[待定问题](#open-questions)

## 核心问题 {#core-problem}

参验的实验验证目前只覆盖文档。Phase 2 全量实验验证了文档的语义校验拖底能力，过程文档检查项分层验证初步验证了检查项匹配文档类型的有效性。代码的参验路径二尚未设计，也未验证。

代码和文档的参验共享同一套哲学基础即 PRO-07 鉴的反映与 PRO-08 应辨的处置，但两者的检查对象形态不同。文档的检查对象是 claim、论证、声明，代码的检查对象是接口、行为、副作用。如果分别独立设计，可能产生两套不一致的参验协议，增加维护成本与认知负担。

本提案要解决的具体问题：等 sih-engine 有实际代码后，如何设计代码参验路径二，使其与文档参验路径二在哲学基础与协议结构上一致，在检查项上匹配代码形态，并且与 SDD 加 TDD 开发范式嵌合而非重叠。

## 候选方案 {#candidates}

候选方案一 代码路径二独立设计
: 待审议
: 等有代码后，针对代码形态独立设计路径二检查项，不复用文档参验的协议结构。拒绝理由：独立设计会产生两套协议，哲学基础重复论证，维护成本高。且代码与文档在治理环中都经参验节点，两套协议使参验组件内部出现分叉，违背参验作为单一组件的设计。

候选方案二 代码路径二直接复用文档检查项
: 待审议
: 把文档的三项检查项即引用有效性、操作完整性、约束一致性或核心文档三项直接用于代码。拒绝理由：文档检查项的基准是 claim 与 upstream_overview，代码没有这些结构。代码的基准是意图声明与 spec，强行复用会导致检查项与检查对象错配，重蹈过程文档检查项错配的覆辙。

候选方案三 SDD 加 TDD 嵌合下的缝隙检查
: 待审议
: 承认 SDD 加 TDD 已覆盖路径一全部与偏差三维中的两个半。代码路径二只查 SDD 加 TDD 的三个缝隙。拒绝理由：此方案最精确但依赖 SDD 加 TDD 范式被实际采用。若 sih-engine 代码开发未采用此范式，三个缝隙的定义不成立，须回退到更通用的检查项设计。

## 推荐方案 {#recommended}

推荐候选方案三即 SDD 加 TDD 嵌合下的缝隙检查，前提是 sih-engine 代码开发采用 SDD 加 TDD 范式。

三个缝隙检查项如下。检查项一过度实现检测，代码的公开接口清单中是否有 spec 未要求的接口，基准是 SDD spec，对照物是代码公开接口。检查项二 spec 完整性，意图声明的每个要求是否都在 spec 中有对应定义，基准是意图声明，对照物是 spec。检查项三测试覆盖完整性，spec 的每个定义是否都有对应测试，基准是 spec，对照物是测试清单。三项基准层层递进，意图声明到 spec 到测试到代码，每一层对照上一层查缝隙。

若 sih-engine 未采用 SDD 加 TDD，回退到候选方案一的独立设计，以意图对齐、副作用边界、可复现性三项为代码路径二检查项。此回退方案在本提案对话中已初步推导，但未经验证。

文档侧的对应扩展。DES-006 参验基准预置机制目前覆盖文档修改场景。等代码参验设计时，将文档的 spec 驱动参验从修改场景扩展到创建场景，使每份治理文档创建前定义检查对象清单，创建后参验对照清单检查。代码是 spec 驱动开发，文档是 spec 驱动参验，共同点是检查对象事前定义不事后提取。

## 哲学检索 {#philosophy-search}

哲学仓检索结果如下。

PRO-07 鉴的反映义约束适用于代码参验。鉴只反映事实不判断好坏，代码参验的反映层呈现代码与 spec 的差异事实，不判断代码好坏。原文路径 sih-philosophy/emanation/proodos/07-on-assay.md。

PRO-08 应辨的处置义约束适用于代码参验。偏差即已抵达的挑战，过度实现与低度实现归应辨处置。原文路径 sih-philosophy/emanation/proodos/08-on-settle.md。

convergence 层 P1.2.2 偏差三维适用于代码。不一致即代码行为与意图冲突，过度实现即代码做了意图未要求的，低度实现即代码遗漏了意图要求的。

工程基线第一条即确定性程序是治理操作的唯一执行者，约束代码参验的副作用边界检查项。工程基线第四条即操作结果可机械校验，约束代码参验的可复现性检查项。

## 待定问题 {#open-questions}

待定问题一。SDD 加 TDD 范式是否被 sih-engine 代码开发采用。若采用，候选方案三成立。若不采用，须回退到候选方案一。此问题待 sih-engine 进入代码实现阶段后确认。

待定问题二。代码参验路径二的检查项能否像文档参验一样达到可接受的 auto-decide 率。代码的语义比文档更结构化，信号可能更明确，收敛可能更好。但代码的行为空间远大于文档的声明空间，意图对齐判断可能更复杂。此假设需像 Phase 2 一样跑实验验证，不能凭推理下结论。

待定问题三。文档 spec 驱动参验从修改场景扩展到创建场景后，检查对象清单的定义成本是否可接受。每份文档创建前定义清单增加前置工作量，若成本高于偏差修复成本则收益不足。此问题待实践中量化。

待定问题四。过程文档检查项分层验证目前只跑了 3 文档初步验证。draft 抽样 10 文档的任务包已生成，待 mmx M2.7 跑完后聚合分析。若 draft 验证通过，过程文档专用检查项的有效性得到更强支撑，代码参验的检查项设计可参照分层思路。

## 认识论立场 {#epistemic-stance}

本提案为设计推论（design-corollary），是工程设计方向的登记，非已验证的机制。

可证伪条件一
: 若 sih-engine 代码开发未采用 SDD 加 TDD，候选方案三的三个缝隙检查项不成立，须回退到更通用的检查项设计。

可证伪条件二
: 若代码参验路径二实验验证的 auto-decide 率低于可接受阈值，代码参验路径二的拖底能力不成立，须重新设计或搁置。
