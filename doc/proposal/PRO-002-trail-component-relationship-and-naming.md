# trail 物理载体与操作组件的关系界定及立名方向

本提案登记一个待审议的治理方案：界定 trail 物理载体与操作 trail 的组件之间的关系，并登记操作组件的立名方向。本提案不立即实施，登记以待审议。审议通过后，由后续 DEC 承载立名决策，由后续 DES 与 SPEC 承载关系界定的落地。

## 概览 {#overview}

- trail 物理载体已在 DEC-001 登记名字，操作组件未立名，两者混在事件流一个名下::[核心问题](#core-problem)
- 两个候选含维持现状与拆分两层，各含拒绝理由::[候选方案](#candidates)
- 推荐拆分两层，trail 为物理载体，操作组件独立命名承接 PRO-08 应而不藏的留痕载体职能::[推荐方案](#recommended)
- 哲学基础 PRO-08 应而不藏留痕是构成性条件、PRO-09 元层治理框架自身须被治理、PRO-01 立名本体论::[哲学检索](#philosophy-search)
- 两个待定问题含组件具体名字与 record_trail 是否独立::[待定问题](#open-questions)

## 核心问题 {#core-problem}

DEC-001 第 131 行登记了 trail 节点，语义是治理主体动作的实时伴随留痕，这是物理载体层。DEC-001 第 144 行明确事件层与状态层的物理载体由后续设计文档承载，本决策只定本体二分的逻辑结构。

DES-003 第 81 行定义了事件流组件，语义是追加写入治理操作事件提供检索与回放，承接 PRO-08 应而不藏。这是操作组件层。DES-003 把组件名、物理载体、数据格式、哈希链、校验规则全部塞在第 81 至 93 行的一个小节里，没有独立的决策说清楚三件事。

第一，事件流这个组件名的立名依据是什么。参验有 DEC-002 专门立名，论证工程名贴工程职能与承古典出处。事件流没有对应的立名决策，事件流只是数据结构的描述，不是哲学职能的描述。

第二，事件流组件与 trail 物理载体的关系是什么。事件流是操作 trail 的组件，类比数据库表与 ORM 模型的关系，trail 是被操作的对象，事件流是操作者。这一关系当前未显式定义，散落在 DEC-001 与 DES-003 与 SPEC-004 三处。

第三，record_trail 作为操作 trail 的执行入口为什么没有名字。它在 SETSP 是独立 Tool 层，在 sih-engine 当前实现里被事件流组件吸收，没有独立的治理地位。这导致手动构造 trail 行时没有可对照的独立契约，契约散落三处使手动模拟易遗漏字段。

本提案要解决的具体问题：界定 trail 物理载体与操作组件的关系，使哲学承接显式化，为后续立名决策提供审议基础。

## 候选方案 {#candidates}

候选方案一 维持现状不拆分
: 待审议
: 事件流既是操作 trail 的组件名，也涵盖 trail 物理载体的操作语义，不拆分。拒绝理由：事件流是数据结构描述不是哲学职能描述，承接 PRO-08 应而不藏的留痕载体职能未被显式声明，违反 PRO-09 元层要求治理框架变更自带防御机制。record_trail 执行入口无名的问题无法解。手动构造 trail 行无独立契约的问题无法解。哲学承接不明使组件在本体论地位上处于有名无实的立名失败形态，承接 PRO-01-naming-failure 即名字承诺与实体运作错位。

候选方案二 拆分为两层
: 待审议
: trail 是物理载体，操作组件独立命名，承接 PRO-08 应而不藏的留痕载体职能。组件名待后续 DEC 立名，本提案只登记方向。拒绝理由：拆分需修订 DES-003 与 SPEC-004，修订期间两层定义处于过渡态，过渡态内手动构造 trail 行的契约参照会有短暂不一致。且 record_trail 的归属判定即操作组件子功能还是独立组件会增加组件清单复杂度。这些代价被评估为可接受，方案仍被推荐，但代价真实存在不是零成本。

## 推荐方案 {#recommended}

推荐候选方案二即拆分为两层。

拆分的哲学依据。PRO-08 第 114 行原文，应的反馈需要载体，载体是留痕，留痕不是治理的附属品，是应鉴循环的构成性条件。写 trail 的组件承接 PRO-08 应层的留痕载体职能。此承接关系当前未显式声明，是核心问题的根因。

拆分的边界。trail 物理载体承载发生过的事件，是只追加写的 NDJSON 文件，归 DEC-001 事件层 trail 节点。操作组件承载写入、校验、检索三个职能，承接 PRO-08 应而不藏的留痕载体职能，归独立命名的组件。操作组件不承接应的动作职能即应辨处理已抵达挑战与应几预判微兆，也不承接鉴的职能即 PRO-08 第 178 行应不替代鉴。操作组件只承接留痕这一载体职能。

立名方向。操作组件的名字应承接留痕载体职能，类比参验立名即 DEC-002 工程名贴工程职能承古典出处不硬套哲学命题。具体名字待后续 DEC 立名决策承载，本提案不预定名字，只登记立名须承接 PRO-08 留痕载体职能这一方向。record_trail 作为执行入口是否独立于操作组件，待定问题二承载。

## 哲学检索 {#philosophy-search}

哲学仓检索结果如下。

PRO-08 应而不藏适用于操作组件的职能承接。原文第 114 行，应的反馈需要载体，载体是留痕，留痕是应鉴循环的构成性条件。写 trail 的组件承接应层的留痕载体职能。原文路径 sih-philosophy/emanation/proodos/08-on-settle.md。边界约束是 PRO-08 第 178 至 184 行应不替代鉴，操作组件只承接留痕载体不承接鉴的检验职能。

PRO-09 元层适用于治理框架自身须被治理。操作组件当前没有走立名决策路线，是治理框架的事实变更未带防御机制，违反 PRO-09 第 84 行任何治理框架的变更必须自带防御机制。原文路径 sih-philosophy/emanation/proodos/09-on-arche.md。

PRO-01 立名本体论适用于操作组件的立名必要性。PRO-01 第 14 行，名字是本体，一个名字一旦确立它参与构成被命名者。操作组件当前用事件流这个数据结构描述作名，是名字承诺与实体运作错位即 PRO-01-naming-failure。原文路径 sih-philosophy/emanation/proodos/01-ontology-of-names.md。

## 待定问题 {#open-questions}

待定问题一。操作组件的具体名字。本提案只登记立名方向即承接 PRO-08 留痕载体职能，不预定名字。具体名字由后续 DEC 立名决策承载，须论证工程名贴工程职能与承古典出处，类比参验 DEC-002 的立名方法。

待定问题二。record_trail 执行入口是否独立于操作组件。SETSP 把 record_trail 定义为独立 Tool 层，sih-engine 当前实现把它吸收进事件流组件。拆分两层后，record_trail 是操作组件的子功能还是独立组件，此问题待拆分方案审议后由后续 DEC 或 DES 承载。

## 认识论立场 {#epistemic-stance}

本提案为设计推论（design-corollary），是工程设计方向的登记，非已验证的机制。

关系界定为外部锚定（external-anchor），承接 PRO-08 与 PRO-09 与 PRO-01 三项哲学命题。立名方向为设计推论，是工程约定。

可证伪条件一
: 若实践中拆分两层导致操作组件与 trail 物理载体的边界频繁模糊，即同一动作难以判定归载体还是归组件，则拆分判据须重新审视。

可证伪条件二
: 若后续 DEC 立名时发现没有合适的工程名能贴留痕载体职能，即所有候选名都与实体运作错位，则立名方向须重新审视，可能须回退到候选方案一即维持事件流名。
