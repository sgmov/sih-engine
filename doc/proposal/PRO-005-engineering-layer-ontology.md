# 引擎层级本体论立名方向提案

本提案登记一个待审议的治理方案：确立司衡引擎的工程层级本体论，含五层分级定义、领域结构、组件两类形态、各层级归属判据。本提案不立即实施，审议通过后由后续 DEC 承载立名决策。

本提案承接本轮层级讨论的全部推导，依据是 SETSP 与旧仓与外仓三个源的层级词频采样，以及用户对 worktree 加 2locks 基础设施定位的判定。本提案分阶段产出，承接 OQ-12 信息洪流内建防护。

## 核心问题 {#core-problem}

司衡引擎当前在用的层级词有六个：引擎、基础设施、组件、模块、单元、节点。这六个词散落在已立文档与代码中，未走立名决策。

核心断点是单元与组件的名实不符。三问在旧仓定名为三问单元，但旧仓给单元的定名释义是边界自洽、生命周期独立、具备完整输入输出闭环的认知计算主体，这描述的是组件特征不是单元特征。旧仓用单元的唯一理由是避开 iCL 与 iWW 与 iCT 三机的机字，新仓无三机，避开机字的理由不存在。

三问承接应几哲学命题，有明确接口，是治理动作网关，按职能定位是组件。单元应回到最小功能原子的本义，承接 PRO-004 的语义节点。

名实不符违反 PRO-01 立名本体论。名字是本体，名字一旦确立参与构成被命名者。三问叫单元会框定后续推导沿单元的承诺展开，但三问的实际运作是组件，两者最终脱节。这条脱节在本轮已实际发生，PRO-004 把语义单元用于最小语义节点，与三问单元的单元同词不同义，造成概念混淆。

层级边界与判据不明放大了这条混淆。组件与模块的边界靠工程约定，模块与单元的边界靠粒度直觉，无立名判据。后续新治理对象须先判定属于哪一层，无判据则命名随机。

## 层级结构 {#layer-structure}

层级关系有两类，不混。

垂直分层。基础设施在引擎之内，领域在基础设施之上展开。这是上下层关系，上层依赖下层提供运行前提，下层不感知上层的治理职能。

包含关系。领域含组件，组件含模块，模块含单元。这是嵌套关系，外层包含内层，内层是外层的构成部分。

领域不是与五层并列的第六层。领域是多组件联动涌现的治理效果。单个组件不产出治理效果，效果永远在联动中涌现。视图组件单独存在无意义，须联动书简拿 trail 留痕、联动参验拿文档语义分析结果、联动判定器拿结构性分析结果，聚合后才产出减少人类介入这个治理效果。领域是这类联动效果的抽象总称，不是静态层级。

## 层级定义 {#layer-definitions}

### 引擎 {#layer-engine}

整体身份，承载一切。本仓实例是 sih-engine。引擎是命名锚点，所有层级与领域都在引擎之内。

### 基础设施 {#layer-infrastructure}

治理运行前提，不承接哲学命题。基础设施提供组件运行所需的物理与计算基础，组件不感知基础设施的实现差异。

已确认子项。worktree 加 2locks 即并发隔离与文件锁，是治理运行前提。度量服务即微积分计算器，承载偏离率与置信度等确定性数学计算。hash 与时间戳即底层原语，trail 哈希链与 stable id 派生都依赖。持久化即项目级记忆与文件数据库增删改查。索引即分词与精确查找，读 AST 切分语义单元挂 stable id，按标识符确定性定位。

待判定子项归后续 DEC 承载，见待定问题一。

### 组件 {#layer-component}

治理动作网关，有明确接口，承接哲学命题。组件是治理领域的入口，每个组件承接至少一项哲学命题的工程职能。

组件分两类，都是组件，都在领域层展开。

直接治理动作组件。承接单一哲学命题的治理网关。参验承接鉴的反映职能，书简承接应的留痕载体职能，三问承接应几的前向约束职能。

聚合输出组件。联动多组件，聚合产出供人类介入。视图承接 FM-04 人类只在视图告警时介入，是介入点的接口。视图组件单独存在无意义，须联动直接治理动作组件的产出。

### 模块 {#layer-module}

组件内部可插拔实现，组件不感知实现差异。同一组件可换不同模块，模块替换不改变组件接口。

本仓实例。事件流模块即 src/event_stream 已实现。存储模块可以是内存或文件或数据库，组件调存储模块的抽象接口不感知具体实现。

### 单元 {#layer-unit}

模块内部的最小功能原子，不可再分。单元是数据与操作的最小粒度。

数据单元。单条 trail 记录、单个语义节点、单条规则反例。

操作单元。单次参验校验、单次书简写入、单次偏离率计算。

## 全态 {#full-state}

全态是司衡引擎开发完毕的形态，且 sih-engine 与其所有组件正常展开级联工作。全态是领域的运行态补全：领域是多组件联动涌现的治理效果，全态是这个联动闭合后的运行形态本身。

全态的级联涵盖工具调用链。级联的调用图合法跨过治理边界，三问调用筛的谓词件、引擎手动调用 facet，工具在治理上自治、在级联中被调用。全态即引擎组件级联加工具调用链。

信息洪流治理与全态的同一关系。全态的运行效果即失配治理，材料流与注意力预算的动态匹配即损补的动态化，减少人类介入这个涌现效果与防洪目标是同一句话。信息洪流的治理不是全态里的一个功能，是全态的运行效果本身。

全态是运行态非封存态。到达全态后损补节律仍在运转，判据再校准、席位基线重测、规则退出与替换照常进行。全态指建造完毕与级联闭合，不指系统静止。

全态给建造侧提供知止锚点。法三要求每条规则能回答何时停止生效，全态回答建造侧的同一问题即什么叫做完了。无完成参照态的建造是治理自增殖的候选样本。

全态是渐进逼近的。引擎当前 src 仅有 event_stream，三问在提案阶段，任务包 007-013 已起草未执行，外围工具先于核心成熟是当前实况。由此登记路线图收敛结论：信息洪流一体双面的工程落地与引擎建造是同一份路线图的两种视角，排序的统一裁决标准是哪一步让级联更早闭合哪一步先做。

全态的逼近路径是外切孵化融回范式。引擎开发经四步环：外切 sih-tools 分解、skills 手工调用验证、效果符合可证伪验收判据、经可插拔机制融回为组件模块实现。facet 为已验证先例。三纪律随范式携带即接口契约先于工具本体、验证判据前置、治理自增殖守望。治理边界据此改述为孵化膜：sih-tools 孵化期治理自治，融回后模块进引擎治理域，单独发布能力并行保留。主线锁见 GOV-002。

签署记录：全态概念、同一关系与外切孵化融回范式于 2026-08-19 会话由用户签署登记，登记位置随本提案层级本体论一起，本提案整体的候选方案审议状态不变。

## 候选方案 {#candidates}

候选方案一 维持现状不立名
: 待审议
: 接受六个层级词混用，不走立名决策。拒绝理由：名实不符会自我放大，PRO-01 立名本体论第 22 行明确，名字与实体错位会导致后续推导沿名字承诺展开，实体沿另一路径演化，两者最终完全脱节。三问叫单元已实际造成与语义单元的概念混淆，不立名则混淆扩散。

候选方案二 部分立名只统一单元与组件
: 待审议
: 只立名三问从单元正名为组件，不立名完整五层分级。拒绝理由：只解单元与组件的混淆，不解组件与模块、模块与单元的边界判据。后续新治理对象仍须判定属于哪一层，无判据则命名随机。部分立名是头痛医头，五层的边界须一次性确立。

候选方案三 全量立名五层分级
: 待审议
: 立名五层分级定义、领域结构、组件两类形态、各层级归属判据。拒绝理由：全量立名的工程量大于前两候选。此代价被评估为可接受，因层级本体论是元层决策，影响所有后续治理对象的命名，元层决策的立名成本一次性付出长期受益。

## 推荐方案 {#recommended}

推荐候选方案三即全量立名五层分级。

立名依据。PRO-01 立名本体论，名字是本体，名字一旦确立参与构成被命名者。层级名框定该层对象的可能内涵，叫组件的东西不会被期待是最小原子，叫单元的东西不会被期待有明确接口。层级立名后，后续新治理对象的命名须先判定属于哪一层，按层级的名实承诺取名。

立名范围。五层定义即引擎、基础设施、组件、模块、单元。领域结构即领域是多组件联动涌现的治理效果，非独立层。组件两类形态即直接治理动作与聚合输出。各层级归属判据即依据是否承接哲学命题、是否有明确接口、是否可插拔、是否最小原子四条判据组合判定。

认识论立场。层级本体论是工程约定，非哲学承接。哲学仓的流衍链即道法鉴应是哲学命题的分级，不是工程实现层级。哲学给的是治理职能分工，不是工程对象粒度。这条立场须在 DEC 显式声明，避免后续误把工程层级当哲学命题。

立名不立即修订已有文档。PRO-003 三问单元的正名与 skill 措辞同步，归 DEC 立名后的统一修订，不在本提案承载。

## 哲学检索 {#philosophy-search}

哲学仓检索结果如下。

PRO-01 立名本体论适用于层级立名的必要性。原文 sih-philosophy/emanation/proodos/01-ontology-of-names.md 第 14 行，名字是本体，一个名字一旦确立它参与构成被命名者。第 16 行，名字框定被命名者的可能内涵。第 22 行，立名失败的形态是名字与实体错位，错位会自我放大。三问叫单元是立名失败形态，正名为组件是修正。

PRO-09 元层适用于层级本体论的治理地位。原文 sih-philosophy/emanation/proodos/09-on-arche.md。层级本体论是治理框架自身的结构定义，属于元层治理对象。元层要求治理框架变更须自带防御机制，层级立名的防御机制是五层归属判据，每个新治理对象须按判据判定层级。

工程基线第一条确定性程序是治理操作的唯一执行者适用于基础设施层的定位。基础设施层承载确定性程序，不承接哲学命题。度量服务、hash 与时间戳、索引都是确定性程序的承载。

哲学不直接指导工程层级。哲学仓的流衍链是哲学命题的分级，不是工程实现层级。工程五层是工程层设计决策，认识论立场是工程约定非哲学承接。这条在推荐方案已声明。

法三知止与法四损补适用于全态的停止锚点与运行态定位。原文 sih-philosophy/emanation/proodos/06-on-canon.md 第 69 行，司衡的每一条规则都应能回答这条规则何时停止生效。第 75 行至第 79 行，损补具有周期性，校准不是一次性动作是持续性节律。全态给建造侧提供知止锚点，全态的运行态定位即损补节律在级联闭合后的持续运转。

## 待定问题 {#open-questions}

待定问题一。基础设施子项完整清单。本提案确认了五项子项即 worktree 加 2locks、度量服务、hash 与时间戳、持久化、索引。SETSP 与旧仓还有驱动、中间件、适配器等形态出现。驱动归原语类即 hash 与时间戳，中间件归运行时类即 worktree 加 2locks，适配器归模块形态即存储模块的具体实现。这三类不单列基础设施子项，归入已确认子项的实现形态。倾向此归类，待 DEC 确认。

待定问题二。领域的正式命名。领域是本轮讨论中确定的命名，指多组件联动涌现的治理效果。领域是否作为正式命名进 DEC，还是作为描述性概念保留。倾向正式命名，因领域须在后续设计文档中稳定引用。

待定问题三。运行时是否单列。运行时在 SETSP 与旧仓是高频词，worktree 加 2locks 与度量服务等都在运行时承载。倾向运行时是基础设施的描述维度不是独立层级，与网关是组件特征不是独立层同理。待 DEC 确认。

待定问题四。子系统是否预留。SETSP 出现 29 次子系统，旧仓无。子系统粒度大于组件，指多组件协作群。倾向当前不预留，因组件数少无须分组管理。若后续组件数增长到须分组，再立子系统。

## 认识论立场 {#epistemic-stance}

本提案为设计推论即 design-corollary，是工程设计方向的登记，非已验证的机制。

层级五分与领域结构为工程约定即 engineering-convention，非哲学承接。层级立名的依据承接 PRO-01 立名本体论，但层级本身的五分选择是工程决策，哲学仓无对应命题。

可证伪条件一
: 若五层归属判据在实践中无法稳定判定新治理对象的层级，即同一对象按不同判据归入不同层，则五分结构须重新审视，可能须合并或拆分层级。

可证伪条件二
: 若领域作为多组件联动效果的定位在实践中无法与组件层区分，即领域退化组件层的同义重复，则领域概念须重新审视，可能须取消领域只保留组件层。
